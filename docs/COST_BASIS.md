# 持仓周期、摊薄成本与综合盈亏

## 用途

在原有**移动平均成本**和 AKShare 行情显示的基础上，为每只**当前仍持有**的股票计算当前持仓周期的已实现盈亏、摊薄成本、综合盈亏。无需增加 QQ 指令，也不改动已经入账的成本或数据库表结构。

所有计算只读：不更改 `holdings`、`trades`、原始成本、买卖盈亏或单笔撤回/恢复行为。

## 定义和公式

- **持仓总成本**：现有 `holdings.total_cost`，保持用于未来 `BUY` / `SELL` 的移动平均成本。
- **周期已实现盈亏**：当前持仓周期内所有**生效中的部分卖出**产生的 `trades.realized_pnl` 之和。盈利、亏损都累计。
- **摊薄成本（每股）**：`(持仓总成本 - 周期已实现盈亏) / 当前持仓数量`。允许为负。
- **持仓浮盈亏**：`当前市值 - 持仓总成本`，只有获得同币种有效行情时才能计算。
- **综合盈亏**：`持仓浮盈亏 + 周期已实现盈亏`，不得再重复抵扣/加算摊薄成本。

> 本功能**不显示“综合收益率”**：反复买卖后选择什么金额作为收益率分母容易产生歧义。原始浮盈亏率仍然保持不变。

### 示例

持仓 100 股、每股成本 10；卖出 20 股、成交价 12（已实现 +40）；再以 9 元买回 20 股。

| 指标 | 结果 |
| --- | ---: |
| 当前持仓 | 100 股 |
| 移动平均成本 | 9.80/股 |
| 周期已实现盈亏 | +40.00 |
| 摊薄成本 | 9.40/股 |
| 假设最新价 | 11.00/股 |
| 持仓浮盈亏 | +120.00 |
| 综合盈亏 | +160.00 |

以上价格为模拟数值，不是真实行情。

## 周期边界

对 **同一平台、同一 QQ 群、同一用户、同一股票代码** 的交易，按 SQLite `trades.rowid`（实际插入顺序）遍历**生效中的交易记录**：

1. `BUY`：不直接改变已实现盈亏。
2. `SELL` 且 `quantity_after > 0`：计入本次已实现盈亏（也可能是负数）。
3. `SELL` 且 `quantity_after = 0`：全仓卖出，结束旧周期；重新买入后累计从 0 开始。
4. `SET`：无论数量是 0 还是非 0，均重置当前周期的已实现盈亏；覆盖校准不代表成交。
5. `is_active = 0`（已撤回的输入）：完全忽略，不参与已实现盈亏，也不形成周期边界。再次恢复时会重新计入。

只统计**当前仍有持仓**的用户和股票；已清仓周期的历史盈利留在 `trades` 中，不会误抵扣新一轮持仓。不能仅依赖 `/持仓 历史` 的最近 10 条记录，否则长期做 T 会漏算。

旧数据库中存在的历史记录只要包含有效的 `realized_pnl`，也会参与相应在持周期的计算；如果没有可用历史，则按累计已实现 0 显示。

## 群内公开和权限

- `/持仓 查看`、`/持仓 查看 #编号`：展示所查询群友当前持仓的**移动平均成本、摊薄成本、周期已实现、浮盈亏和综合盈亏**。
- `/持仓 汇总`：按标的和币种，对**当前仍持有该标的的群成员**合计持仓总成本与各成员自身周期已实现盈亏，然后计算群加权摊薄成本与综合盈亏。
- `/持仓 历史`：仍然只能查询发送者自己的最近操作，不能指定其他人或其他群，也不在公开回复里展示任何逐笔交易记录。
- 从 QQ 平台事件得到 `(platform_id, group_id, user_id)`；所有人只能在当前群查看本群的公开持仓。

## 行情可用性

- 已实现盈亏和摊薄成本**无需行情**，包括日股、美股和港股，只要用户曾使用插件登记有效的买卖记录即可计算。
- 浮盈亏和综合盈亏必须有同币种行情。当前 AKTools MCP 行情第一阶段仅支持 A 股，其余市场及行情请求失败时标注**综合盈亏暂不可计算**，不使用 0 元假行情。
- 汇总的已报价 A 股小计只包含本页中成功取得报价的人民币持仓；缺价时标明“部分”。不同币种不得相加。
- 已实现盈亏是记录价格与移动成本差的计算值，不包括尚未建模的手续费、税费或分红。

## 数据库与兼容性

无数据库迁移、无新字段，继续使用 `PRAGMA user_version=4`。新版仅增加按当前持仓周期读取并求和 `trades.realized_pnl` 的只读逻辑，使用 Python `Decimal`，不使用 SQLite `SUM(TEXT)` 可能导致的浮点误差。

升级前仍建议备份 `data/plugin_data/astrbot_plugin_portfolio/portfolio.db`。
